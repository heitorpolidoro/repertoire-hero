4. Stage chrome — a question for you

docs/use-cases.md says reading and annotating should look different: with drawing off you should see the page and one small button at the bottom; the full toolbar should only appear once you turn drawing on. That change applies to PDFs exactly as much as to photos, so it is not needed to make photos work. This spec leaves it out and proposes it as the next task (option A). Compare the two below.

A — what this task ships (toolbar always visible)
✏️ Draw: Off Pen/Erase/Pan − 100% + Saved

Reading and drawing look the same. One toolbar row, not two — a photo is a single page, so the ‹ Prev / Page 1 / 1 / Next › row from section 2 is not rendered at all, and the Saved chip sits in the toolbar instead. That row is about 60 px of the roughly 390 px a sideways phone gives the stage: about a sixth, not the quarter two rows would have cost.

B — the use-case chrome, pulled into this task

Reading shows the page and one button; the toolbar from A appears only after tapping it. It buys back that sixth while reading — and the same sixth on every PDF, which is why it is really its own task.

Answer with one letter. A = ship photos now with the toolbar as it is today, and do the chrome change as its own task next. B = hold this task until the chrome change ships with it.
Honest note: an earlier draft of this question claimed the bar eats a quarter of a sideways phone. With the page row gone for a single-page photo it is closer to a sixth, so the screen-space argument for doing B now is weaker than it first looked — the remaining argument for B is only that reading and drawing still look identical.
